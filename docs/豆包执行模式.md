# 豆包执行模式（Doubao Execution Mode）

建立日期：2026-09-21。适用范围：豆包（Doubao）客户端执行本仓库文案任务时生效；Codex 及其他客户端仍按 AGENTS.md 与共享规则原样执行。

本文件只记录经用户确认的表达层执行调整。事实与合规底线（真实性、来源可追溯、禁编造、禁夸大、禁贬损、参数边界、新闻核验）不因本文件改变。

## 调整 1：生成流程内部简化（对应清单 C6）

- 完整文案的生成阶段按 `generation-trigger-registry.md` 的流程在内部按序执行，不省略门禁。
- 中间阶段记录、临时内容状态、阶段清单默认不落盘、不展示给用户；交付物（标题、最终口播文案、必要资料出处）保持不变。
- 内部仍须通过：事实门、承诺可回答检查、受众价值检查、口播审查、篇幅与内容覆盖、结构去重、反向答案检查、一句话总结检查、新闻落点检查（新闻稿）、事实复检、B2B 质量门、合规词表复检。

## 调整 2：审查方式按载体执行（对应清单 D3；2026-09-22 与调整 3 对齐）

- 豆包端默认两用时，完整稿按 `docs/豆包书面图文模式.md` 的书面审稿标准自查（保留长句与信息密度，查拖沓/冗余/新闻堆砌/AI 腔），不再强制逐稿走 humanizer 口播重写流程。
- 用户明确要求"短视频口播""抖音口播""口播稿"时，才按 `expression-craft.md` 的口播验收标准自查；此时不再默认书面审稿。
- 高风险稿（涉及法规、精确参数、新闻、认证、强因果）保留抽查；发现症状时按对应载体的审查标准处理。
- 自查不得放宽事实命题、限定条件、因果强度与责任关系。

## 调整 3：默认表达载体为书面+口播两用（2026-09-22 确认）

- 豆包端完整文案默认按 `docs/豆包书面图文模式.md` 的书面+口播两用标准执行：书面结构起稿（新闻锚点→痛点→产品对比→明确推荐→公司落地→顾问式收尾）、书面审稿（保留长句与信息密度，查拖沓/冗余/新闻堆砌/AI 腔，不查碎句/钩子）、顾问式收尾。
- 用户明确要求"短视频口播""抖音口播""口播稿"时，按 AGENTS.md 抖音口播逻辑执行（前 0–3 秒钩子、完播、口语节奏、动作结尾）。
- 未指定载体时不再默认口播，而是默认两用；减少用户每次说明载体的成本。
- 门禁不减：事实门、承诺可回答检查、受众价值检查、篇幅与内容覆盖、结构去重、反向答案检查、一句话总结检查、新闻落点检查（新闻稿）、事实复检、B2B 质量门、合规词表复检全部保留，仅将口播审查按书面审稿重解释。
- 本调整覆盖"未调整部分"C 组中的钩子与结尾两项在豆包默认场景下的执行方式；结构、标题、篇幅、去重仍按原规则保留。
